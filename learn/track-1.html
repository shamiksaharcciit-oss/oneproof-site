Learn onetrace track 1 · nine levels · about two hours

Record, check, compare.

Nine levels on your own machine, with onetrace 0.5.0 and the console. Each level says what to do, what its output must be, and what the verifier must say for it to pass. Most levels build on the one before, so do them in order and keep every folder: they are your proof, and the badge's inputs later.

Before you start The levels When you're done

Before you start

What you need.

Python 3.12 or newer

And a terminal. Windows, macOS and Linux all work; the commands are given for each where they differ.

onetrace 0.5.0 installed

pip install onetrace in a virtual environment, as in Get started; the console is not needed for this track. Nothing is sent anywhere by any level except 1.8, which says so.

A folder you keep

Everything below goes under one project folder. Keep its runs/ when you finish: each level's folder is its proof.

How a level passes. Not by you saying so: by the verifier's line, the comparison's verdict, or, on the detective level, the console's own short answer. Every level states the exact line to look for.

The levels

Nine levels, in order.

1.1 First run

Set up a folder with a virtual environment and install onetrace, exactly as in Get started, steps 1 to 3. Then create app.py from step 4 there: a retrieve stage and an answer stage, with a TOP_K setting. Add one line as the first line inside retrieve, so the setting is recorded by name:

    ot.constant("top_k", TOP_K)

Record your first run with a fixed run id, so the level's folder has a known name:

Windows (PowerShell)

$env:ONETRACE_RUN_ID = "level-1"
python app.py
onetrace-verify --require-artifacts runs/level-1

macOS or Linux (Terminal)

ONETRACE_RUN_ID=level-1 python app.py
onetrace-verify --require-artifacts runs/level-1

Pass when: the last line reads -> PASS with 0 fail, and runs/level-1/receipts/ holds three receipts: 01-intake.json (the question going in), 02-retrieve.json and 03-answer.json. Lines marked NOT-RUN name checks this record doesn't use; they are not failures.

Badge: first verified run. Keep runs/level-1.

1.2 Break it

Copy the level 1 folder to runs/level-2. Open runs/level-2/receipts/03-answer.json in a text editor. The receipt is one long line; find "outputs", and in its digest change the first character after sha256: to another hex digit. Save, then verify:

onetrace-verify --require-artifacts runs/level-2

Pass when: the first line reads record NOT intact: receipts/03-answer.json: digest matches the manifest (3 failing rows) and the summary ends -> FAIL. The three [FAIL] rows are: the receipt's digest no longer matches the manifest; the output file return.json no longer matches the digest the receipt now claims for it, with the expected and found digests printed; and the chain head no longer matches the last receipt. Nothing else fails. You changed one character; the record says which file, which value, and that the chain no longer closes.

Now the lesson's other half: put the character back exactly, verify again, and the run passes. A record is bytes; the check is on the bytes.

Badge: saw the chain hold. Keep runs/level-2, restored, and the verifier's output as text; the refusal is the output.

1.3 Two runs

In app.py, change TOP_K = 1 to TOP_K = 2. Record a second run and compare it with the first:

Windows (PowerShell)

$env:ONETRACE_RUN_ID = "level-3"
python app.py
onetrace localize runs/level-1 runs/level-3 --out r3

macOS or Linux (Terminal)

ONETRACE_RUN_ID=level-3 python app.py
onetrace localize runs/level-1 runs/level-3 --out r3

Pass when: the first line after the two run names reads localize: diverged; the ladder reads intake same, retrieve FIRST DIFFERENCE and answer reconverged; under retrieve it lists constant top_k differs and output return.json differs; and the CAUSE at node 'retrieve' block names constant top_k differs again, with the instrument unchanged. The command exits 1, which is what "the runs differ" looks like to a script (echo $LASTEXITCODE in PowerShell, echo $? in a terminal).

Read reconverged carefully: it is the lesson of this level. Retrieve now returns two passages, so its output differs; but the answer stage uses only the first passage, which is the same, so the answer's output is identical. A setting changed, an intermediate result changed, and the final answer did not. The record shows exactly where the difference started and where it stopped. r3/localize.json is the same answer as data.

Badge: found the first difference. Keep runs/level-3 and the comparison report r3/.

1.4 Detective, on the live demo

On the live demo, open pipeline P1 and the two runs p1-02-baseline-set2 and p1-08-candidate-set2. Do not open their comparison yet. From the two run pages alone, answer three questions: at which stage do the outputs first differ, which setting differs there, and what are its two values?

Then open the comparison between them. The short answer at the top is one sentence, from the records and no model.

Pass when: your three answers equal the short answer's. If they don't, read the stage pages again: every number on them comes from a receipt.

Badge: read the record. Your answer is the output; the console's short answer is the check.

1.5 Noise

Set TOP_K back to 1 and record the example once more, as level-5. Compare it with level 1:

onetrace diff runs/level-1 runs/level-5

Nothing you control changed, and the comparison may still find differences: a run id, a timestamp, a path. That is release noise. Ask onetrace what to mask, read each line (a version change can be a real cause, not noise), then save the suggestion and compare again with it:

onetrace mask suggest runs/level-1 runs/level-5
onetrace mask suggest runs/level-1 runs/level-5 --json > mask.json
onetrace diff runs/level-1 runs/level-5 --mask mask.json

Pass when: the masked comparison reads identical after masking (exit 0), and every row the mask changed says so. If the first comparison was already identical, the example recorded no noise; the level still passes, and mask.json is empty, which is also an answer.

Badge: masked the noise. Keep runs/level-5 and mask.json.

1.6 Keep an input, then erase it

Inputs are fingerprinted, not stored. Keeping one is a choice you make per input, in the decorator: add keep_inputs=["question"] to the retrieve stage (the manual's section 16.19 gives the exact form and the size cap). Record level-6 and verify it; the folder now holds inputs/ with the question's text.

Now erase it: delete runs/level-6/inputs/ entirely, and verify again.

onetrace-verify --require-artifacts runs/level-6
onetrace diff runs/level-1 runs/level-6 --text

Pass when: the run still verifies after the deletion (a receipt holds the input's digest, never its text), and the text comparison reads not kept: file missing for that input. You have kept a value, and taken it back, without touching the record.

Badge: kept and erased. Keep runs/level-6, with its inputs/ removed.

1.7 Sign

Follow Get started, step 8 exactly: make a key once in a folder outside your project, sign the level 1 run copied as runs/level-7, write trust.json with your key id, and verify with it:

onetrace-verify --require-artifacts --trust trust.json runs/level-7

Pass when: the signature line reads PASS with the label from your trust list. Then the break-it half: edit trust.json so the key id has one wrong character and verify again. The same signature now reads SIGNED-UNTRUSTED: valid, but by a key your list doesn't name. Put the id back. A signature shows the record is unchanged since signing; your trust list is what says whose key it is.

Badge: signed it. Keep runs/level-7 and trust.json.

1.8 Timestamp (this level goes online)

This is the one onetrace command that uses the network, and it sends only the run's fingerprint. Follow Get started, step 9 with the level 7 folder copied as runs/level-8: fetch the authority's two certificate files, anchor the run, and verify with them:

onetrace-verify --require-artifacts --trust trust.json --tsa-cert tsa.crt --tsa-root tsa-root.pem runs/level-8

Pass when: the check gains a PASS line for anchors/1.json with the attested time. Without the two certificate files, the anchor can't be checked and the verifier says so; that is the right reading, not a failure of the record.

Badge: committed to a time. Keep runs/level-8 and the two certificate files.

1.9 Reproduce

A comparison says what differs between two runs. Reproduce asks a different question: if the recorded code runs again, does it give the recorded outputs? It needs a runner file that says how to run your code; write runner.json as the manual's section 10.3 gives it, with "code": "app.py". Then reproduce the level 5 run, the last one recorded with app.py as it is now:

onetrace reproduce runs/level-5 --runner runner.json --out r9

Pass when: each stage reads REPRODUCED, or COULD NOT CHECK with its reason named (the code's digest no longer equals the recorded one, if you edited app.py after level 5, say). Either is a pass: the level is about reading what reproduce can and cannot say, and COULD NOT CHECK is never "close enough". A DIVERGED stage is also a reading, and worth a look at r9/: the code ran, and gave something else.

Badge: reproduced a stage. Keep the reproduce report r9/.

When you're done

Nine folders, one chain.

You now hold nine run folders and three reports, every one checkable by anyone with onetrace-verify, and you have seen the verifier refuse twice for reasons it named. That is the whole method of onetrace, done by hand once. When the onetrace quest command ships, it reads these folders, checks each level's shape, and writes your badge records from them, signed with the key you made at level 1.7. Keep the folders until then.
